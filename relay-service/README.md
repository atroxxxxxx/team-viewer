# Ретранслятор

Место ретранслятора на диаграмме контейнеров — в [C4](../docs/uml/c4-container.png). Отчёт — в корневом [README.md](../README.md#c4).

Сервис на Go со своим Redis и без базы. Redis хранит UUID клиента, `tunnel_id` и два секрета сессии. Начальный TTL составляет 15 минут. Сервис заявок продлевает его, пока сеанс активен. Туда же пишется id заявки, чтобы снять туннель при закрытии. Секреты сравниваются по хешу, в журнал не пишутся.

Сервис заявок может быть на другом сервере. Наружу открыты два порта:

| Порт | Кто | Зачем |
| --- | --- | --- |
| `18082` | сервис заявок | `POST /api/v1/tunnels` после утверждения, `DELETE /api/v1/tunnels/{ticket}?tunnel_id=…` отзывает конкретный туннель. `POST /api/v1/tunnels/{ticket}/renew?tunnel_id=…` продлевает его. Заголовок `Authorization: Bearer` |
| `8554` | клиент и оператор | Первая строка `CLIENT <tunnel_id> <секрет>` или `OPERATOR <tunnel_id> <секрет>`, не длиннее 200 байт. Дальше по соединению идёт RTSP |

RTSP слушает только `127.0.0.1:18554` внутри процесса. Сессионный порт проверяет, что uuid есть в Redis и что секрет совпал с секретом заявленной роли. Каждое RTSP-соединение использует проверенные роль и ID туннеля. Клиент публикует, оператор смотрит. Камера доступна только при разрешении в заявке. Поток не публикуется отдельным портом в интернет. Приложения на своих машинах принимают ffmpeg на localhost и прокидывают байты в порт `8554`. Тело `POST /api/v1/tunnels` ограничено 1 МБ.

`GET /health` на порту `18082` проверяет Redis.

Отдельный запуск: `docker compose -f relay-service/docker-compose.yaml up -d --build`. Перед сборкой образа рекомендуется `go mod vendor` в этом каталоге: Docker берёт зависимости из `vendor` и не ходит за ними в сеть.

Кто какой порт принимает, записано в [SECURITY.md](SECURITY.md). Риски и планы — в [RISKS.md](RISKS.md) и [PLANS.md](PLANS.md).
