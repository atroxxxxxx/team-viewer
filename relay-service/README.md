# Ретранслятор RTSP

Отдельный сервис на Go. Один RTSP-порт принимает экран клиента и отдаёт его оператору. Камера — второе исходящее TCP на тот же порт и отдельный путь той же сессии, если клиент включил её в заявке. Команд и чата здесь нет.

Оба участника открывают исходящее соединение. Новый порт на сессию не выделяется, TLS и UDP для RTP не используются: пакеты идут внутри RTSP по TCP. Смотреть и публиковать путь можно только с токеном, который записал сервис заявок в Redis. Без токена `DESCRIBE` и `ANNOUNCE` получают 401. Издатель делает `ANNOUNCE` и `RECORD`, зритель — `DESCRIBE`, `SETUP` и `PLAY`. Когда сервис заявок удаляет токен, отдельного HTTP-вызова сюда нет: следующая команда получает 401.

Путь экрана: `/sessions/{ticket_id}/screen`. Путь камеры: `/sessions/{ticket_id}/camera`. Токен передаётся параметром `token` в RTSP URL.

## HTTP

| Метод | Зачем |
| --- | --- |
| `GET /health` | Процесс и Redis |
| `GET /api/v1/paths` | Какие пути сейчас опубликованы, без токенов |

Swagger при живом сертификате: `https://127.0.0.1/swagger/relay/index.html`. Спека: `https://127.0.0.1/openapi/relay.json`. Если сертификата нет, страница остаётся на `http://127.0.0.1:8080/swagger/relay/index.html`. HTTP процесса опубликован на `127.0.0.1:18081`. Корень с localhost перенаправляет на `/swagger/index.html`, с другого адреса соединение закрывается без ответа. `GET /api/v1/paths` отвечает только оператору с базовой аутентификацией. Публикация и просмотр RTSP по-прежнему идут по токену заявки: клиент не логинится в HTTP ретранслятора. RTSP опубликован на хосте как `8554`, иначе клиент не откроет исходящее соединение.

## Логи и ELK

JSON в stdout. Доставка в ELK — пунктир на диаграмме [07](../docs/uml/07-log-shipping.md), в поставке её нет.
