# PostgreSQL и Redis

Одно хранилище на два процесса: PostgreSQL держит заявки, Redis держит захват, присутствие и медиатокены. Ретранслятор в базу кадры не пишет.

Порты `5432` и `6379` на хост не публикуются. К ним обращаются сервисы заявок и ретранслятора по именам `postgres` и `redis` во внутренней сети compose. Пароль в `docker-compose.yml` годится для локального прототипа.

## Секции

Заявки и связанные таблицы секционированы по `LIST (shard_id)` на четыре секции: `*_s0` … `*_s3`. Номер считает сервис заявок, `crc32(account_id) % 4`, и записывает его в строку. Первичный ключ везде начинается с `shard_id`, поэтому секцию позже можно отсоединить и перенести на другой узел без смены схемы.

`shard_directory` хранит, где лежит секция. Сейчас у всех строк `status = local` и пустой `dsn`: один Postgres обслуживает все секции. `ticket_index` — маленький несекционированный указатель `ticket_id -> shard_id`, чтобы найти заявку по id, не обходя узлы.

Таблицы планов, чата, разрешений и подтверждений созданы и секционированы тем же ключом. Сервис заявок пишет в них из текущих методов сессии.

## Redis

| Ключ | Зачем |
| --- | --- |
| `media:token:{sha256}` | Роль, пути и заявка. Сырого токена нет |
| `media:hashes:{ticket}` | Хеши токенов заявки, чтобы удалить их при `resolved` |
| `lock:ticket:{id}` | `SETNX`, один оператор, 8 часов |
| `ticket:{id}` | Статус и номер секции |
| `presence:ticket:{id}` | Клиент и оператор в сессии |
| `queue:tickets` | Событие после `media` со статусом экрана `up`, не в момент создания заявки |

## ELK

СПЕЦПОМЕТКА. Elasticsearch, Logstash и Kibana в эту папку не входят. Сервисы пишут JSON в stdout. Будущий сбор этих строк показан пунктиром на диаграмме [07](../docs/uml/07-log-shipping.md). `action_log` в PostgreSQL остаётся журналом заявок, а не индексом ELK.
