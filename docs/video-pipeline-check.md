# Проверка настроек, соединения и видео

Проверено 3 ноября 2026 года. Это результаты предыдущего профиля 15 FPS. Обновлённая проверка от 6 ноября с замером отрисовки Qt: [30 FPS](video-30fps-check.md).

## Автоматические проверки

Пройдено 90 целевых Python-тестов и тесты Go-пакетов `internal/rtsp`, `internal/session`.

Целевые Python-тесты охватывают отдельные файлы клиента/оператора, атомарное сохранение настроек, повторное чтение в новом процессе, повреждённые и устаревшие файлы, запрет сохранения секретов, ошибки соединения и HTTP, восстановление после сбоя, автоматическое изменение очереди без ручного обновления, сохранение выделения/прокрутки, отсутствие параллельных опросов, применение настроек через настоящий Qt-диалог и отмену фоновых действий при закрытии.

Отдельно проверены FFmpeg-аргументы, сборка полных RGB-кадров при частичных чтениях stdout и пропуск старых кадров при перегрузке GUI. Окна запущены с `QT_QPA_PLATFORM=offscreen`, оформление проверено по снимкам. Это не проверка управления реальным удалённым компьютером.

## Методика измерения видео

macOS arm64, FFmpeg 8.1, gortsplib 4.16.2 (та же версия, что в relay). Временный RTSP-сервер слушал только `127.0.0.1:19554`. Издатель и плеер использовали сборщики аргументов из `media.py`; для сравнения старые сборщики извлечены из текущего HEAD `1ba027e`.

Вместо X11 использован программный источник RGB 640×360 с шаблоном и двоичной меткой номера кадра. Для каждого кадра фиксировалось монотонное время его подачи на stdin кодировщика; после декодирования метка читалась из RGB-кадра. Измеренная задержка включает кодирование, локальный RTSP, декодирование и чтение stdout. Она не включает реальный захват экрана, сессионные мосты, WAN и финальную отрисовку Qt.

Публикация уже шла 2,31 с к моменту подключения зрителя. Процент CPU получен через `ps` отдельно для процессов FFmpeg; 100% соответствует одному полностью занятому ядру. Python-источник не включён в эти цифры. Материал преимущественно статический, поэтому цифры не характеризуют видеоигры или полноэкранное видео.

| Проверка | Старый пайплайн | Новый, прогон 1 | Новый, прогон 2 |
| --- | --- | --- | --- |
| Наблюдение после подключения | 8 с | 20 с | 12 с |
| Получено кадров | 0 | 288 | 168 |
| Первый кадр после подключения | Не пришёл за 8 с | 0,839 с | 0,835 с |
| Измеренная частота после первого кадра | Нет данных | 15,00 FPS | 15,00 FPS |
| Интервал кадров, медиана / максимум | Нет данных | 67 / 83 мс | 67 / 82 мс |
| Подача кадра → rawvideo, медиана | Нет данных | 139 мс | 138 мс |
| Та же задержка, первая / последняя четверть | Нет данных | 139 / 140 мс | 139 / 137 мс |
| CPU издателя, медиана | 1,35% | 6,20% | 4,85% |
| CPU плеера, медиана | 0,30% | 1,30% | 1,20% |

В наблюдаемые интервалы роста задержки не обнаружено. Старый плеер не получил кадр за 8 с; это нижняя граница ожидания, а не измеренное полное время подключения. Разрешение осталось прежним. Нагрузка нового кодировщика ожидаемо выше из-за роста частоты с 5 до 15 FPS; максимальная частота ограничена 30 FPS и настраивается пользователем.

При подключении через 0,206 с после старта публикации первый кадр пришёл через 0,942 с после подключения; за 6 с наблюдения получено 76 кадров, измеренная частота 15,01 FPS, медиана задержки 140 мс.

Дополнительное кодирование 3 секунд через новый `publish_args` и проверка `ffprobe` дали 45 кадров и ключевые кадры на 0,000, 1,000 и 2,000 с.

Сырые результаты, журналы, код источника и временного RTSP-сервера находятся локально в `.dev/video-check/` (каталог исключён из Git). В измерениях по PTS из раннего пробного прогона была начальная погрешность временной шкалы FFmpeg; в таблице использован только повторный прогон с фактическими метками времени подачи кадров.

Параметры анализа и буферизации сверены с [документацией FFmpeg](https://ffmpeg.org/ffmpeg-formats.html#Format-Options). Значения из пользовательского PROBLEMS.md использованы как исходная диагностика, не как результаты новой проверки.

## Ограничения

Docker не запущен, Redis отсутствует. Полный путь через ticket service, PostgreSQL, Redis, relay и реальный клиент X11 здесь не поднимался. Производственная аутентификация и код relay не изменялись. Перед оценкой задержки реального удалённого управления нужен прогон на двух целевых машинах с настоящим экраном и сетью. Windows/Wayland-захват по-прежнему не реализован существующим бэкендом.


## Исправления после независимого ревью ветки

- Для POST восстановлен бюджет ожидания 15 с при connect timeout 1,5 с: relay может отвечать до 5 с при принятии/закрытии заявки.
- Клиентский OS-ввод исполняется последовательно, отменяется при завершении сеанса и закрытии, повторно проверяет разрешение перед исполнением.
- Отложенные действия оператора не переносятся на другую заявку.
- Ответ на отправленное сообщение/наблюдение не стирает новый черновик.
- Шаги и очередь обновляются по ID, сохраняют выделение и прокрутку при изменении списка.
- Скачивание и выполнение моделей вынесены в управляемые процессы, завершаемые при закрытии окна.
- В инструкции сборки Debian зависимость Qt заменена на `python3-pyqt5`.
