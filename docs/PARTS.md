# Документы трёх частей

Команда делится на три части. Общие диаграммы лежат в [README.md](README.md). Они не заменяют документы части: каждая часть ведёт свой комплект и отвечает за то, чтобы он совпадал с кодом.

| Часть | Каталог | Кто стыкуется |
| --- | --- | --- |
| Сервер заявок | [ticket-service](../ticket-service/README.md) | Принимает заявку, хранит её в PostgreSQL, после утверждения вызывает ретранслятор |
| Ретранслятор | [relay-service](../relay-service/README.md) | Принимает утверждённую заявку в Redis и склеивает сессию клиента и оператора |
| Клиент и оператор | [client-app](../client-app/README.md), [operator-app](../operator-app/README.md) | Одна часть на оба окна. Клиент кладёт заявку, оператор её забирает и подключается к сессии |

## Обязательный комплект

В каталоге части лежат четыре файла. Чужую часть этими файлами не описывают.

| Файл | О чём писать |
| --- | --- |
| `README.md` | Общее описание решения: зачем часть, её граница, какие данные хранит, какие порты открывает, как стыкуется с двумя другими |
| `SECURITY.md` | Безопасность: кто кому доверяет, чем доказывается вызов, какие секреты есть, что не должно быть доступно из сети |
| `RISKS.md` | Риски: что может сломаться или быть использовано не так, какой ущерб, что уже закрыто, что ещё открыто |
| `PLANS.md` | Планы только этой части: что будет сделано дальше и чего в поставке ещё нет |

Для части «клиент и оператор» комплект один на оба окна. `README.md` каждого окна остаётся его описанием. `SECURITY.md`, `RISKS.md` и `PLANS.md` лежат в `client-app/` и покрывают оба приложения. `operator-app/README.md` на них ссылается, второй комплект в `operator-app/` не заводится.

## Что считается готовым

Файл описывает текущее поведение части, а не отменённый вариант. Если граница изменилась, правится комплект той части, которой граница принадлежит, и при необходимости общая диаграмма в [README.md](README.md).

Пустой заголовок без текста не считается документом. В `SECURITY.md` должен быть ответ, какой вызов часть принимает и какой отвергает. В `RISKS.md` у каждого риска есть последствие. В `PLANS.md` пункт либо сделан в коде, либо явно назван будущим.
