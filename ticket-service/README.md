# Сервис заявок

HTTP-сервис на Go (Gin). Прототип создаёт заявку, ставит её в очередь после публикации экрана, отдаёт оператору захват и ведёт чат, план, разрешение на ввод и двойное подтверждение. Таблицы этих сценариев секционированы тем же ключом.

Заявку создаёт клиент с базовой аутентификацией. Логин `client`, пароль совпадает с `client-app/config.yaml` и `CLIENT_PASSWORD`. Очередь, захват и правки оператора требуют логин `operator`. Дальнейшие вызовы клиента по уже созданной заявке несут заголовок `X-Ticket-Token` с токеном издателя: чужой id заявки без этого токена не открывается. Роль в чате и в подтверждении берётся из учётной записи, а не из тела запроса.

Процесс не хранит сессию в памяти. Заявки лежат в PostgreSQL, захват и медиатокен — в Redis. Несколько экземпляров читают одну базу. Номер секции считает приложение: `crc32(account_id) % 4`. Каталог `shard_directory` пока помечает все четыре секции как `local`, и процесс пишет в один пул. Поле `dsn` зарезервировано под вынос секции на другой узел. Ключ таблиц для этого уже включает `shard_id`, схему менять не придётся.

## Что отвечает сейчас

| Метод | Кто | Зачем |
| --- | --- | --- |
| `POST /api/v1/tickets` | клиент | Заявка, секция, токен издателя, пути экрана и камеры |
| `POST /api/v1/tickets/{id}/media` | клиент и токен издателя | Экран публикуется, статус `queued`, событие `queue:tickets` |
| `GET /api/v1/tickets` | оператор | Очередь из PostgreSQL |
| `GET /api/v1/tickets/{id}` | оператор или клиент с токеном | Описание и статус |
| `POST /api/v1/tickets/{id}/claim` | оператор | Один оператор, токен читателя. Идентификатор берётся из логина |
| `GET /api/v1/tickets/{id}/session` | оператор или клиент с токеном | Чат, шаги, грант, ожидающий ввод |
| `POST /api/v1/tickets/{id}/messages` | участник сессии | Чат. Автор — роль учётки |
| `POST /api/v1/tickets/{id}/control-requests` | оператор, заявка его | Запрос управления, грант `pending` |
| `POST .../control-requests/{grant}/decision` | клиент и токен издателя | `remote_control` или `guided`. Scope только `pointer`, `key`, `text` |
| `POST /api/v1/tickets/{id}/input` | оператор, заявка его | Событие ввода, фаза `proposed` |
| `POST .../input/{action}/result` | клиент и токен издателя | `applied` или `rejected_by_client` |
| `POST /api/v1/tickets/{id}/actions` | оператор, заявка его | Отказ правил, `blocked_by_policy` |
| `POST /api/v1/tickets/{id}/plans` | оператор, заявка его | План шагов |
| `POST .../steps/{step}/observations` | клиент и токен издателя | Наблюдение по шагу |
| `POST .../steps/{step}/complete` | оператор, заявка его | Шаг `done`, если наблюдение уже есть или оператор пишет «вижу на экране» |
| `POST .../steps/{step}/revise` | оператор, заявка его | Старый шаг `cancelled`, новый `todo` |
| `POST /api/v1/tickets/{id}/problems` | оператор, заявка его | Дочерняя проблема. Родительский шаг должен быть в этой заявке |
| `POST /api/v1/tickets/{id}/resolution` | участник сессии | Подтверждение. Роль берётся из учётки |

Тело запроса ограничено 1 МБ, план — 20 шагами. Медиатокены издателя и читателя живут 12 часов, блокировка захвата — 8 часов, активный грант управления — 30 минут. Статусы заявки: `created`, `queued`, `assigned`, `awaiting_permission`, `remote_control`, `guided`, `awaiting_client`, `resolved`.

Сырой токен возвращается один раз. В базе и в Redis лежит только его хеш.

## Swagger

Страница при живом сертификате: `https://127.0.0.1/swagger/tickets/index.html`. Спека: `https://127.0.0.1/openapi/tickets.json`. Процесс слушает `18080` и на хосте опубликован только как `127.0.0.1:18080`. Снаружи к API ведёт nginx. Пока сертификат есть, HTTP только перенаправляет на HTTPS. Если сертификата нет, та же страница открывается на `http://127.0.0.1:8080/swagger/tickets/index.html`. Публичное имя `TICKET_DOMAIN` после Let's Encrypt отдаёт `/api/` и `/health` по HTTPS, а порт 80 этого имени перенаправляет туда же. Swagger с публичного имени не отдаётся. Swagger, `/health` и `/openapi.json` на самом процессе без Basic.

## Логи и ELK

Каждая строка — JSON в stdout. Сбор в Logstash, Elasticsearch и Kibana на диаграмме [07](../docs/uml/07-log-shipping.md) показан пунктиром и в эту поставку не входит. Журнал `action_log` в PostgreSQL — отдельный контур, его в ELK не выгружаем.
